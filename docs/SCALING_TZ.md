# ТЗ: 25 камер на сервере 2 × RTX 5090

Перенос всей AI-нагрузки (fight, fire, face, counting, heatmap, persons) с 25
камер на один Linux-сервер с двумя RTX 5090 — без потери событий, без
накопления очередей и с измеримой задержкой.

Статус: решения заказчика согласованы 20.10.2026 (§8). Числа с пометкой
**[оценка]** — ориентир до замера; решения, которые от них зависят, исполнитель
принимает по итогам этапа 0 (§6) по правилам из §3 и §5.7 и записывает в этот
документ.

Затрагивает два репозитория:
- `aimekeme` — AI-API (модели, этот репозиторий);
- `vision` — платформа (broker: чтение камер, такты модулей, эпизоды, UI).

Связанные документы: `docs/architecture_full.png` (целевая схема при
масштабировании), `vision/platform/TZ.md`, `vision/DEPLOYMENT.md`,
`docs/CONVENTIONS.md`.

---

## 1. Цель и критерии успеха

На сервере 2 × RTX 5090 одновременно работают все 25 камер со всеми модулями:
fight, fire, face, counting, heatmap (+ persons по событию face).

Успех — это одновременно:
1. Пропущенных тактов модулей (`module_skips`) не больше 1% при полной нагрузке.
2. Задержка укладывается в согласованные цели по каждому модулю, p95 (§4.2).
3. 24 часа под полной нагрузкой без падений, утечек и «тихой» деградации (§4.3).
4. Отказ одной GPU не выключает тревожные модули (fight, fire).
5. Снимки, клипы и кроп лица — в родном разрешении камеры, как сейчас.

## 2. Как устроено сейчас

### 2.1 Поток данных

```
Камера (RTSP, основной поток Channels/101)
  -> vision: CameraWorker (поток на камеру, cv2.VideoCapture, декод на CPU)
  -> HTTP JSON, кадры JPEG в base64
  -> aimekeme: один процесс FastAPI, все модели на одной GPU, lock на модель
  -> ответ -> сглаживание N-из-M / медиана -> эпизоды -> PostgreSQL + WebSocket
Живое видео: камера -> go2rtc -> браузер (мимо AI)
```

Камеры читает **платформа** (broker внутри backend `vision`). AI-API ничего не
хранит между запросами (stateless).

### 2.2 Модули и частоты (vision `platform/backend/app/config.py`)

Сейчас на всех 25 камерах включены face, counting, heatmap (`cameras_export.json`),
на одной — ещё обход PTZ. fight и fire будут включены на всех.

| Модуль | Когда вызывается | Что уходит в AI-API | Подтверждение |
|---|---|---|---|
| fight | каждые `fight_step`=**16** кадров при полном fps источника (окна не перекрываются) | 16 JPEG 224×224 | 2 из 3 |
| fire | раз в 1.5 с | 1 JPEG ≤1280 по ширине; в AI-API режется на 2×2 + кадр целиком = 5 картинок SigLIP2 | 3 из 5, fire и smoke раздельно |
| face | раз в 0.5 с | 1 JPEG ≤640 | 2 из 5 на identity |
| counting | раз в 1 с | 1 JPEG ≤640, yolo_head | медиана 6 |
| heatmap | раз в 8 с | 1 JPEG ≤640, `/detect/counting?for_heatmap`, FRCNN | — |
| persons | при новом face-событии | 1 кадр родного разрешения | — |

`fight_step`: в `config.py` по умолчанию 4, решение — 16 (§8). Выставить 16
в `config.py` и проверить значение на странице «Параметры». Остальные значения
тоже могут быть переопределены там (`tuning.eff`) — перед этапом 0 снять
фактические значения из базы.

### 2.3 Найденные узкие места и дефекты

| # | Где | Суть | Последствие на 25 камерах |
|---|---|---|---|

Для H.264/H.265 пропустить декод кадров нельзя в принципе: стоимость декода = разрешение × fps источника, сколько бы кадров ни брали модули | 25 основных потоков декодируются на CPU целиком. С fight это главный потребитель CPU и источник отставания |
| D2 | vision `worker.py:378` | `CAP_PROP_BUFFERSIZE` бэкендом FFmpeg не поддерживается, вызов молча ничего не делает | При отставании декода кадры копятся, модели видят прошлое |
| D3 | aimekeme, все детекторы | Один `threading.Lock` на модель, один процесс | Пропускная способность модели = 1 / (время под lock). face: 50 запр/с (§3) — на грани одного процесса |
| D4 | aimekeme `counting/detector.py:103` | counting (yolo_head) и heatmap (FRCNN) под одним lock | Медленный FRCNN задерживает подсчёт |

Enroll идёт под тем же lock, что и распознавание | При нескольких процессах новое лицо узнаёт только один из них. Перезагрузка и enroll блокируют распознавание на секунды |
| D6 | aimekeme `face/detector.py:83` | Если CUDAExecutionProvider не поднялся, face молча работает на CPU | На CPU face не тянет даже текущую нагрузку (зафиксировано в vision `config.py`, 28.08.2026). Ошибка не видна при старте |
| D7 | aimekeme, все детекторы | Нет прогрева моделей при старте | Первые запросы после рестарта в разы медленнее; при таймауте модуль слепнет |
| D8 | vision `config.py` `ai_timeout_s=15` | Пока запрос висит, busy-флаг блокирует модуль камеры | Один зависший запрос = модуль камеры слеп до 15 с |
| D9 | aimekeme `req.txt` (незакоммичено) | `triton`, `nccl`, `cufile`, `nvshmem` закомментированы ради Windows | На Linux-сервере окружение соберётся не с теми версиями |
| D10 | сеть | Через Tailscale наблюдали 17–30 с на запрос при 20–30 мс модели (vision `worker.py:187`) | Задержку определяет сеть, а не GPU |
| D11 | aimekeme `face/model.py` | onnxruntime на CUDA перестраивает ArcFace и genderage при **каждой** смене размера батча (= числа лиц в кадре). Замер на RTX 4060 Ti: смена 4<->8 лиц стоит ArcFace ~40 мс, genderage 170–780 мс, и так на каждой смене; `cudnn_conv_algo_search` не помогает | Число лиц меняется от кадра к кадру — face регулярно отвечал сотни мс. Вероятно, это и есть «от полусекунды до нескольких секунд» из vision `config.py` |
| D12 | драйвер GPU | В простое карта уходит в P8 (замер: 210 МГц через ~20 с простоя); первые запросы после простоя fight 150–160 мс вместо 27 | Всплески задержки после пауз (ночь, перерывы, GPU0 с малой нагрузкой) |

Проверено, не дефект: `track_id` в `/detect/persons` уникален только внутри
одного ответа; платформа так им и пользуется (`ai_client.detect_persons_batch`).
Несколько процессов AI-API на это не влияют.

## 3. Расчёт нагрузки на GPU

Допущение: источник 25 к/с (проверяется на этапе 0). 25 камер, все модули.

| Модуль | Запросов/с на камеру | Всего, запр/с | Максимум времени под lock при 1 процессе* |
|---|---|---|---|
| fight | 25 / 16 = 1.56 | 39 | 15.4 мс |
| face | 2 | **50** | 12 мс |
| counting | 1 | 25 | 24 мс |
| fire | 0.67 | 16.7 | 36 мс |
| heatmap | 0.125 | 3.1 | 190 мс |
| persons | по событиям | пики в начале пар | — |
| **Итого** | | **≈ 134** | |

\* Правило запаса: загрузка lock-а ≤ 60%, т. е. `rate × t_lock ≤ 0.6`. Остаток —
на всплески.

**Правила, по которым принимаются решения после замеров (этап 0):**
- Число процессов для модуля: `N = ceil(rate × t_lock / 0.6)`, где `t_lock` —
  измеренное время под lock (p95) при `bs=1`.
- Если для fight `N > 1`, вместо второго процесса делается микробатчинг fight
  (§5.4, A6).
- Загрузка каждой GPU по `nvidia-smi` при полной нагрузке ≤ 60%. Если выше —
  этап 3 (FP16/TensorRT).

**[оценка]** Самый рискованный модуль — face (50 запр/с, до 30–40 лиц в кадре).
Остальные имеют запас в разы.

**Замер на сервере (23.10.2026, этап 0.2/0.4).** Камера (ауд. 119): H.264
1920×1080, **20 к/с** (не 25) — fight при шаге 16 даёт 31 запр/с. Модели по
одной, кадр той же камеры, `scripts/bench_models.py`:

| Модель | t_lock p95, 1 процесс | 1 процесс тянет при 60% | 2 процесса на карте вместе |
|---|---|---|---|
| fight | 2.8 мс | 216 запр/с | 309 |
| face | 7.6 мс | 79 | 86 |
| counting | 4.5 мс | 133 | 136 |
| fire | 11.5 мс | 52 | 76 |
| heatmap | 15.6 мс | 38 | 36 |
| persons | 6.8 мс | 89 | 91 |

Решения по правилам §3: всем хватает одного процесса, микробатчинг fight (A6)
не нужен. Второй процесс на карте почти не прибавляет (face 79 → 86: упор в
GPU, а не в lock) — оставлен ради резерва. Занятость по t_lock × нагрузка:
GPU0 (fight, fire) ≈ 27%, GPU1 (face, counting, heatmap) ≈ 54% — близко к 60%,
поэтому counting/heatmap перенесены на GPU0 (§5.2, только nginx): ≈ 43% и 38%.
Модели здесь работали по одной; под смешанной нагрузкой 25 камер — проверка на
этапе 1. Один процесс AI-API со всеми моделями — 2.4 ГБ видеопамяти. Старт
процесса 2.3 с (первый на новой карте — дольше: onnxruntime один раз
компилирует ядра под Blackwell, прогрев face 23 с вместо 0.2).

**Декод видео.** Объём = 25 × fps × разрешение основного потока. Например,
4 Мп × 25 к/с = 625 кадров 4 Мп в секунду. На CPU это десятки ядер. В RTX 5090
по спецификации NVIDIA 2 аппаратных декодера NVDEC, на сервере их 4. Хватит
ли — проверяется на этапе 0 (0.3).

**Видеопамять.** Все модели вместе с CUDA-контекстом занимают единицы ГБ
**[оценка]**. На карте 32 ГБ, поэтому каждый процесс AI-API грузит все модели
целиком. Это и даёт резерв при отказе.

## 4. Требования

### 4.1 Функциональные

- Контракты AI-API (`/detect/*`, `/faces*`, `/health`) не меняются. Добавляется
  только `GET /stats` (§4.4).
- Логика платформы (эпизоды, N-из-M, клипы, PTZ, UI) не меняется. Меняются
  способ получения кадров (§5.3), таймауты (§5.5) и `fight_step` (§2.2).
- Снимок по кнопке, кадры клипа, кроп лица и кадр для persons — в родном
  разрешении камеры, как сейчас. Превью — не реже 10 к/с, как сейчас.
- Код AI-API остаётся модульным монолитом (`docs/CONVENTIONS.md`): меняется
  развёртывание (несколько экземпляров), а не структура кода.

### 4.2 Задержки (цели согласованы)

Задержка, которую видит оператор, состоит из трёх частей:

- **T_cam** — камера (кодирование), сеть, буфер декодера. Обычно 0.2–0.5 с
  **[оценка]**, меряется на этапе 0.
- **T_alg** — алгоритмическая. Её задают параметры (окно, частота, N-из-M), а не
  железо; уменьшить её можно только сменой параметров.
- **T_conv** — конвейер: от момента, когда кадр попал в broker, до события в
  WebSocket. Её и уменьшает эта работа.

| Модуль | T_alg при согласованных параметрах | Цель T_conv, p95 | **Цель для оператора, p95** |
|---|---|---|---|
| fight | 1.0–1.6 с **[оценка]** (окно 0.64 с, шаг 0.64 с, 2 из 3) | ≤ 0.3 с | **≤ 2 с** |
| face | 0.5–1.0 с (раз в 0.5 с, 2 из 5) | ≤ 0.4 с | **≤ 2 с** |
| fire | 3.0–4.5 с (раз в 1.5 с, 3 из 5) | ≤ 0.5 с | **≤ 6 с** |
| counting | 3–4 с (медиана 6 замеров раз в 1 с) | ≤ 0.5 с | **≤ 5 с** |
| heatmap | минуты (накопление) | ≤ 2 с | — |

**fight при шаге 16 — на границе цели.** Сумма T_cam + T_alg + T_conv по
оценке 1.5–2.4 с. Правило: если на приёмке этапа 2 полная задержка fight p95
больше 2 с, исполнитель предлагает заказчику шаг 8. Это даёт T_alg 0.7–1.2 с
при 78 запр/с fight (порог `t_lock` ≤ 7.7 мс). Шаг меняется только после
согласования.

Как меряется:
- T_conv — по временным меткам в платформе (§4.4).
- Полная задержка — секундомер на экране перед камерой: сравнить время на
  экране в кадре с временем события в журнале. Для fight — постановочная сцена.

### 4.3 Надёжность (что значит «без багов»)

| # | Сценарий | Требование |
|---|---|---|
| R1 | 24 ч под полной нагрузкой | Ни одного падения процесса. Рост RAM и VRAM после первого часа ≤ 5%. Пропусков тактов ≤ 1%. У всех камер кадр свежее 5 с |
| R2 | Отключение камеры | Переподключение ≤ 10 с после возврата; остальные камеры не затронуты |
| R3 | `kill -9` процесса AI-API | systemd поднимает его ≤ 30 с; до этого nginx шлёт запросы на резерв; тревожные модули теряют ≤ 5 с |
| R4 | Отказ одной GPU (оба её процесса остановлены) | fight и fire работают на второй карте, T_conv ≤ 2 × цели. face/counting/heatmap допускают пропуски |
| R5 | Добавление лица под нагрузкой | Распознавание на других процессах не блокируется дольше 1 с; новое лицо узнаётся всеми процессами ≤ 5 с после ответа enroll |
| R6 | Перезапуск в любом порядке (AI до платформы и наоборот) | Восстанавливается без ручных действий |
| R7 | Модель должна быть на GPU, а оказалась на CPU | Процесс **не стартует** и пишет причину в лог |
| R8 | Ошибки вызовов AI-API (`module_status.error`) | 0 за прогон, кроме намеренно вызванных отказов |

### 4.4 Наблюдаемость

- **AI-API, `GET /stats`** (новый). Для каждого эндпоинта: число запросов,
  p50/p95 полного времени, p50/p95 **ожидания lock**, p50/p95 инференса. Только
  так можно отличить очередь от медленной модели. Счётчики сбрасываются при
  рестарте.
- **Платформа, `runtime_status`**. Сейчас там `module_calls` (число и сумма мс)
  и `module_skips`. Добавить p95 времени вызова и «возраст кадра»: время от
  поступления кадра в broker до получения ответа. `tests/test_load.py` выводит
  оба числа.
- **GPU**. `tests/test_load.py` (`gpu_info`) дополнить загрузкой NVDEC
  (`utilization.decoder`) и признаками троттлинга (`clocks_throttle_reasons.active`).
- **CPU**. `tests/test_load.py` уже снимает общий CPU и CPU процессов на
  портах; добавить суммарный CPU всех ffmpeg-процессов broker.

## 5. Целевая архитектура

### 5.1 Схема

```
Камеры, 25 шт. (RTSP, основной поток)
  |  1 RTSP-сессия на камеру для анализа (go2rtc держит свою — для живого видео)
  v
vision: broker
  ffmpeg на камеру: NVDEC (камеры поровну на GPU0 / GPU1) -> scale_cuda
    поток "fight": 224x224, полный fps        (берётся, только если fight включён)
    поток "main" : родное разрешение, 10 к/с  -> face, counting, fire, heatmap,
                                                 превью, клипы, снимки, PTZ
  CameraWorker: последний кадр + кольцо из 16 для fight, такты, эпизоды, БД, WS
  |  HTTP на localhost, контракт AI-API без изменений
  v
nginx :8000 — маршрутизация по пути
  /detect/fight, /detect/fire                     -> ai-g0          резерв ai-g1a
  /detect/face, /detect/counting, /detect/persons -> ai-g1a, ai-g1b резерв ai-g0
  POST/DELETE /faces*                             -> ai-g0 (единственный писатель)
  GET /faces*, /health, /stats                    -> любой
  v
aimekeme: один и тот же код, 3 процесса, в каждом все модели
  ai-g0  : CUDA_VISIBLE_DEVICES=0  :8100
  ai-g1a : CUDA_VISIBLE_DEVICES=1  :8101
  ai-g1b : CUDA_VISIBLE_DEVICES=1  :8102
  общая known_faces/ (faces.db + фото), галерея — с эмбеддингами и версией
```

### 5.2 Размещение по GPU — почему так

- **GPU0 — тревожные модули (fight, fire).** Ядра CUDA из разных процессов на
  одной карте делят время. Если fight делит карту с face, его задержка «плавает»
  вместе с числом лиц в аудиториях. Отдельная карта делает задержку тревог
  предсказуемой.
- **GPU1 — face, counting, heatmap, persons.** face — самый тяжёлый модуль;
  два процесса на карте снимают ограничение одного lock (D3).
- **Резерв крест-накрест.** Каждый процесс грузит все модели, поэтому при
  отказе карты nginx отправляет её запросы на другую (R4).
- **Писатель базы лиц — ai-g0.** Enroll считает эмбеддинги под lock face. На
  ai-g0 face работает только как резерв, поэтому enroll не тормозит основное
  распознавание.
- **Балансировка после замеров.** Если при полной нагрузке GPU0 загружена
  меньше 30%, а GPU1 больше 60%, `/detect/counting` (вместе с heatmap)
  переводится на ai-g0. Это правка только конфигурации nginx. Число процессов —
  по правилам §3.

Не нужны: NCCL, NVLink, tensor/pipeline parallel. Каждая модель целиком
помещается на одну карту; масштабирование идёт числом процессов, а не делением
модели.

### 5.3 Приём видео: декод на GPU (vision)

Замена `cv2.VideoCapture` в `CameraWorker` на чтение из `ffmpeg`-процесса с
NVDEC — `vision/platform/backend/app/broker/ffmpeg_source.py` (**сделано
21.10.2026**, проверено на RTX 4060 Ti, см. ниже). Как устроено:

1. **Один ffmpeg-процесс на камеру, два выхода:** `fight` — каждый кадр
   источника, 224×224; `main` — родное разрешение, `MAIN_STREAM_FPS`=10.
   Ветка fight есть всегда (дёшево), воркер просто не берёт её кадры, если
   модуль выключен — без перезапуска ffmpeg при включении/выключении.
2. **Выходы — y4m по TCP на 127.0.0.1.** Две трубы из одного процесса на
   Windows не передать, сокеты одинаково работают везде. Размер кадра и fps —
   из заголовка y4m, а не ffprobe: лишний RTSP-сеанс при каждом подключении —
   лишнее ожидание опорного кадра.
3. **Кадр fight — как раньше давал `cv2.INTER_AREA`.** Прямой `scale_cuda` в
   224 даёт другой кадр (замер PSNR к INTER_AREA: lanczos 22 дБ, bilinear 28 дБ).
   На GPU — ступени не больше чем вдвое до 448, последний шаг — area на CPU по
   маленькому кадру: 31.7 дБ, столько же, сколько у декода на CPU (32.4). Кадры
   main совпадают с кадрами OpenCV на уровне 43 дБ.
4. **Без `-fflags nobuffer`.** Проверено: с ним декод начинается не с опорного
   кадра, и первые секунды до следующего опорного в модели уходит серый мусор.
5. **`-timeout` 3 с у RTSP.** Без него ffmpeg на выключенной камере висит
   бесконечно (проверено) — переподключение ждало бы зависшую попытку.
   Требует ffmpeg ≥ 5 (§5.6).
6. **Читатели всегда опустошают сокеты**, кадр main — только последний, с
   меткой времени поступления (для «возраста кадра», §4.4).
7. **Переподключение:** ffmpeg вышел / нет кадров 5 с → закрыть, пауза 3 с,
   открыть заново. Причина — в `last_error` камеры (текст ffmpeg), счётчик
   `reconnects_total` — в `runtime_status`.
8. **Окно fight:** собирается заново при новом подключении и при паузе между
   кадрами больше 1 с. Порог именно такой: кадры по сети приходят пачками,
   а пропуск по времени прихода в 2 интервала был бы ложной тревогой.
9. **PTZ-обход:** переждать поворот и взять первый кадр main, пришедший после.
10. **Видеофайлы** — тот же ffmpeg с `-re`. **Без NVIDIA** — `DECODE_HWACCEL=none`,
    путь кода тот же. Опечатка в значении — backend не стартует.
11. **Явный отказ:** при `DECODE_HWACCEL=cuda` без рабочего NVDEC камера в
    ошибке с текстом ffmpeg, без тихого перехода на CPU.

Проверено локально (RTX 4060 Ti, запись аудитории 1280×720 12.5 к/с и она же
по RTSP через go2rtc): старт источника 0.6–1.0 с с файла и ~3.8 с с RTSP; все
5 модулей на одной камере без пропусков тактов; возраст кадра к ответу AI p95
75–190 мс (все модели и камера на одной 4060 Ti); обрыв камеры замечен за
0.2 с, восстановление через **5.4 с** после возврата камеры (R2: ≤ 10 с);
28 тестов `vision` зелёные. Не проверено: 25 камер, PTZ-обход (нужна
поворотная камера), Linux.

### 5.6 Сервер и окружение

- **ОС:** Ubuntu 24.04 LTS. Драйвер NVIDIA ≥ 570, открытые модули ядра
  (обязательны для Blackwell). `nvidia-smi -pm 1` (persistence mode).
- **Частоты GPU:** зафиксировать (`nvidia-smi -lgc <мин>,<макс>`, значения — по
  `nvidia-smi -q -d SUPPORTED_CLOCKS`), иначе после простоя первые запросы
  в разы медленнее (D12). Проверка: после 60 с без запросов первый fight не
  дольше p95 устоявшегося режима больше чем в 1.5 раза. Настройку повторять при
  загрузке (systemd-юнит), она не сохраняется после перезагрузки.
- **Питание и охлаждение:** две 5090 по ~575 Вт. Блок питания с запасом,
  температура GPU под 24-часовым прогоном ≤ 83 °C без троттлинга. При
  необходимости — `nvidia-smi -pl` (ограничить мощность). Порог выбирается
  по замеру: потеря скорости против стабильности.
- **Python-стек AI-API:** Python 3.12, `torch 2.9.1+cu128` (поддерживает
  Blackwell), `onnxruntime-gpu 1.23.2` + `insightface 1.0.1 --no-deps`
  (README). Работу CUDAExecutionProvider на 5090 проверить на этапе 0; на это
  же есть A1.
- **ffmpeg ≥ 5** с `-hwaccel cuda` и фильтром `scale_cuda`. Проверка:
  `ffmpeg -hwaccels` содержит `cuda`, `ffmpeg -filters` содержит `scale_cuda`.
  Если сборка из apt без `scale_cuda` — статическая сборка с CUDA-фильтрами.
  ffmpeg 4.x не годится: там `-timeout` у RTSP включает режим сервера (§5.3 п.5).
- **Камеры:** интервал опорных кадров (I-frame interval / GOP) не больше 2 с.
  Каждое подключение ждёт опорного кадра: при GOP в 20 с (так шёл тестовый
  поток) первое подключение не укладывалось в 15 с и R2 не выполнялся.
- **Процессы — systemd**, готовые юниты и пошаговая установка — `deploy/`
  (`deploy/README.md`): `aimekeme@ai-g0`, `@ai-g1a`, `@ai-g1b` (шаблон,
  карта и порт — в `/etc/aimekeme/<имя>.env`), `gpu-clocks`, `vision-backend`,
  `go2rtc`; `nginx` и `postgresql` — штатные. `Restart=always`, `RestartSec=5`.
  Проверены `systemd-analyze verify` на Ubuntu 24.04 (WSL).
- **nginx (AI)** — `deploy/nginx/aimekeme.conf`: upstream'ы по §5.1,
  `max_fails=1 fail_timeout=5s`, `proxy_connect_timeout 1s`. Повтор на резерве —
  `proxy_next_upstream error http_502 http_503 non_idempotent`, **без
  `timeout`**: медленный ответ решает таймаут платформы (P2), а с `max_fails=1`
  nginx по таймауту выключал бы исправный занятой процесс. Только для
  `/detect/*` (они ничего не меняют); для `/faces*` повтор запрещён (двойной
  enroll) и резерва у писателя нет. Проверено на nginx 1.24 (Ubuntu 24.04) с
  заглушками вместо процессов: раскладка по §5.1; при падении ai-g0 fight/fire
  уходят на GPU1, при падении ещё и ai-g1a — на ai-g1b; запись лиц без ai-g0 —
  ошибка (так задумано).
- **Сеть:** сервер в той же сети, что камеры (10.16.x.x), без Tailscale между
  ними (D10). Трафик [оценка]: 25 камер × 4–8 Мбит/с × 2 сессии (broker +
  go2rtc) = 200–400 Мбит/с, сетевая карта ≥ 1 Гбит/с. Если камеры не держат 2
  сессии, broker читает RTSP из go2rtc (`rtsp://127.0.0.1:8554/cam{id}`).
- **Время:** chrony/NTP — метки событий и замеры задержки.

### 5.7 Процессор и память сервера

Модель процессора на момент написания неизвестна. Ниже — минимальные
требования и порядок проверки; исполнитель сверяет с ними фактический сервер
на этапе 0 (шаги 0.1 и 0.7).

**Бюджет CPU при полной нагрузке [оценка]** (основной поток 4 Мп; цены
операций уточняются замером 0.7):

| Работа | Объём на 25 камер | Цена одной операции | Ядер |
|---|---|---|---|
| ffmpeg: выгрузка с GPU + NV12 -> BGR, поток main (родное разрешение, 10 к/с) | 250 кадров/с | 4–8 мс | 1–2 |
| ffmpeg: поток fight 224×224 | 625 кадров/с | < 0.1 мс | < 0.1 |
| broker: JPEG кадров клипа (пре-ролл пишется всегда, родное разрешение, 8 к/с) | 200 кадров/с | 15–25 мс | 3–5 |
| broker: превью (ресайз + JPEG) | 250 кадров/с | 2–4 мс | 0.5–1 |
| broker: кадры для face/counting/fire/heatmap (ресайз + JPEG) | ~95 кадров/с | 2–5 мс | 0.2–0.5 |
| broker: JPEG кадров fight 224×224 | 625 кадров/с | 0.2–0.3 мс | 0.1–0.2 |
| AI-API: декод JPEG, пред- и постобработка | ~134 запр/с | — | 1–2 |
| Python/HTTP/JSON, PostgreSQL, nginx, go2rtc | — | — | 1–2 |
| **Итого** | | | **≈ 7–13** |

**Минимальные требования:**
- CPU x86-64 с AVX2, **не меньше 16 физических ядер**. Это бюджет выше с
  запасом ×1.5–2 на всплески и рост.
- RAM **не меньше 32 ГБ**, рекомендуется 64 ГБ. Три процесса AI-API по 4–6 ГБ,
  25 ffmpeg по 0.1–0.2 ГБ, буферы клипов, PostgreSQL.

**Порядок проверки:**
1. Шаг 0.1: записать модель CPU, число физических ядер (`lscpu`: `Core(s) per
   socket` × `Socket(s)`) и объём RAM (`free -h`).
2. Шаг 0.7: замерить на этом CPU цены операций из таблицы (JPEG родного кадра,
   NV12 -> BGR, ресайз + JPEG 640) и пересчитать столбец «Ядер».
3. Требование к запасу: пересчитанный бюджет ≤ 60% физических ядер. На
   приёмке этапа 2 фактическая загрузка CPU ≤ 70%.

**Если CPU не хватает** — рычаги, которые не меняют разрешение снимков и
клипов, по порядку:
1. Кодировать JPEG клипа и превью на GPU (nvJPEG, например
   `torchvision.io.encode_jpeg` на CUDA-тензоре). Это убирает самую большую
   строку бюджета.
2. Разделить broker на несколько процессов по группам камер (этап 4,
   переносится раньше).

### Этап 3. Ускорение моделей (условный)

Запускается, только если после этапа 2 загрузка GPU > 60% или T_conv вне цели.

Состав: FP16, затем TensorRT для YOLO-моделей (yolo_head, yolov8l-pose,
dfire), X3D, SigLIP2; TensorRT EP для face. Движки TensorRT собираются на самом
сервере (привязаны к архитектуре GPU и версии TensorRT).

**Приёмка — без потери качества** на фиксированном наборе кадров и клипов,
сравнение с FP32:
- fight/fire: метка совпадает в ≥ 99% случаев;
- counting: |Δ числа людей| ≤ 1 на ≥ 99% кадров;
- face: identity совпадает на 100% тестовых кадров, |Δ similarity| ≤ 0.01;
- затем повтор приёмки этапа 2.

### Этап 4. Больше 25 камер (вне рамок, только условия запуска)

Переход к `docs/architecture_full.png` (пул broker-процессов, Redis Streams,
AI-воркеры с батчингом по камерам). Запускать, если:
- камер становится больше, чем тянут две карты по правилам §3; или
- процесс backend упирается в одно ядро (GIL) — проверить `py-spy` под полной
  нагрузкой; или
- CPU не хватает и рычаг 1 из §5.7 не помог.

| FP16/TensorRT меняют ответы моделей | Порог качества в приёмке этапа 3 |
| GIL в процессе backend при 25 камерах | Замер `py-spy` на этапе 2; при упоре — этап 4 |

## 8. Решения и допущения

**Решения заказчика (20.10.2026):**

  сейчас (§5.3).
- Шаг fight — 16 кадров (окна не перекрываются). Переход на 8 — только по
  правилу §4.2 и с согласия заказчика.

§3, §5.7 и записывает сюда):
